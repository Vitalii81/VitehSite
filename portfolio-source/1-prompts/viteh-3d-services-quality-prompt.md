# Завдання: 3D у картках послуг і суттєво кращий рендер 3D-моделей (viteh.org)

Ти працюєш у репозиторії `Vitalii81/VitehSite`. Починай із поточного `main` (він уже містить 3D-галерею з PR #2:
`assets/gallery3d.js`, `assets/vendor/model-viewer.min.js`, `tools/make-models.mjs`, `assets/models/*.glb`, поле `model` у `data/products.json`;
і адмінку-конструктор з PR #3 в `radxa-admin/`). Працюй у новій гілці `claude/3d-quality-services`, відкрий PR у `main`, напряму в `main` не пуш.
Спершу, до коду, напиши в описі PR план на 10–15 рядків. Відповідай українською, код і коментарі в коді англійською.

## Обмеження (як і раніше)

- Сайт статичний, без збірки; **жодних зовнішніх запитів** (GDPR): усе локально в `assets/`. Не змінюй `worker/` і форму контакту.
- Галерея лишається прогресивним покращенням: без WebGL або без скрипта показується плоска картинка. Одна жива 3D-сцена одночасно.
- Не ламай `radxa-admin/`: збірка пакета з порожньою чернеткою має й далі збігатися із заводським сайтом (є тест). Якщо додаєш поле чи файли, які адмінка має знати, онови її схему, перевірки й тести.
- `node --test` і Python-тести адмінки мають проходити. Додай тести на нову логіку.

## Частина 1. Якість 3D-рендера (головне)

Проблема, яку бачить власник: моделі виглядають як «картонні» примітиви. Плата: плоскі сірі та чорні паралелепіпеди, різкі грані без фасок,
циліндри-конденсатори як склеєні шайби, роз'єм і мікросхема без деталей, плата одноколірна без текстури; освітлення плоске, тіні слабкі, краї «драбинкою».
Потрібен помітно якісніший, але все ще легкий результат.

1. **Геометрія в генераторі `tools/make-models.mjs`** (він пише glTF/GLB вручну, без залежностей, і так має лишитись):
   - заокруглені паралелепіпеди (фаска/радіус з 2–3 сегментами) для корпусів, роз'ємів, мікросхем; сфери/циліндри з достатньою кількістю сегментів і **згладженими нормалями** там, де потрібно, та різкими на фасках;
   - деталізація плати: отвори й контактні площадки (кільця), доріжки як тонкі рельєфні смуги, шовкографія (білі прямокутники/позначки як окремі тонкі меші), метал виводів QFP/SOIC, штирьові роз'єми з металевими штирями, електролітичні конденсатори з маркуванням (смужка), SMD-резистори й конденсатори з торцями, кварц, світлодіод зі світним матеріалом;
   - корпус контролера: зазори, вентиляційні прорізи, гвинти, кришка з фаскою, клемні блоки, DIN-захват; датчик: корпус, антена/друкована антена, світлодіод, кабельний ввід.
   - Бюджет: до ~600 КБ на модель у GLB (було 300 КБ; збільши ліміт і в тесті). Використовуй індексовані меші, `Uint16` індекси, спільні матеріали.
2. **Матеріали PBR**: правильні `metallicFactor`/`roughnessFactor` для металу, пластику, текстоліту (глянцева маска), золочених площадок; емісія для світлодіода; зберегти матеріал `accent`, колір якого змінюється за темою (див. `recolor` у `gallery3d.js`).
3. **Текстури без зовнішніх файлів**: за потреби генеруй маленькі PNG/KTX2 прямо в генераторі (наприклад, карту шорсткості/нормалей для текстоліту, шовкографію як baseColor-текстуру на платі). Тримай загальний вага в бюджеті.
4. **Рендер у `<model-viewer>`** (налаштування в `gallery3d.js`):
   - якісне освітлення: збережи `environment-image="neutral"` або поклади локальний `.hdr`/`.exr` невеликого розміру в `assets/vendor/` (з ліцензією CC0 і записом у `assets/vendor/README.md`), підбери `exposure`, `tone-mapping="aces"`/`"agx"` (перевір, що підтримується в наявній версії бібліотеки), `shadow-intensity`, `shadow-softness`;
   - згладжування країв: перевір antialiasing у цільових браузерах, за потреби `max-camera-orbit`/мінімальну відстань, `render-scale`/devicePixelRatio ліміт для телефонів (не вище 2);
   - камера: природніше `field-of-view`, початкова орбіта, плавне автообертання (поважай `prefers-reduced-motion`), обмеження зуму, щоб модель не розтягувалась по краях;
   - постер: генеруй якісні постери (скриншоти моделей) як WebP/PNG невеликого розміру, щоб до завантаження 3D картка не показувала плоский SVG, а гарний кадр моделі. Скрипт для генерації постерів має працювати локально (headless Chrome із програмним WebGL допустимий як розробницький інструмент, не як залежність сайту).
5. **Перевірка якості обов'язкова**: відкрий результат у headless Chromium із програмним WebGL (swiftshader) і додай у PR скріншоти до/після для кожної моделі (великий діалог і картка, світла й темна теми, 390 px і 1440 px). Опиши в PR, що змінилось у кожній моделі.
6. Для справжніх моделей (коли власник їх зробить у Blender) залиш у README короткий робочий процес експорту GLB з Meshopt/Draco і перевірки ваги; не встановлюй нових залежностей.

## Частина 2. 3D у «Послугах»

Зараз 3D є лише на картках розділу «Проєкти». Додай таку саму можливість для карток **послуг** (`services.items` в `data/site.json`).

1. Необов'язкове поле `model` (і за потреби `poster`) у елементах `services.items`. Картки без нього не змінюються. Той самий принцип: код поверх існуючого рендера, без переписування.
2. Повторно використай `gallery3d.js` (одна спільна сцена на всю сторінку, а не окрема для «Проєктів» і «Послуг»). Одночасно активна лише одна 3D-сцена на сторінці.
3. Створи 3 нові процедурні моделі для послуг (тими самими засобами й тієї ж якості, що в частині 1): наприклад, «розробка ПЗ» (стилізований ноутбук або стопка модулів), «електроніка на замовлення» (плата + корпус), «AI-агенти» (стилізований вузол/мережа). Назви й тексти для uk/en/de додай у `site.json` (`ui.gallery3d` ключі вже є, перевір, чи потрібні нові).
4. Переконайся, що **адмінка Radxa** (`radxa-admin/`) не ламається: розділи й послуги можна вмикати/вимикати, а нове поле `model` послуги проходить перевірки (білий список шляхів `assets/models/*.glb`, перевірка існування файла) і потрапляє в пакет. Додай тести. Якщо адмінка вже дозволяє підставляти `.glb` для карток продуктів, зроби те саме для послуг.
5. Якщо WebGL недоступний, не залишай порожнього місця: плоска картинка/іконка послуги, як зараз. Додатково (за бажанням, мала правка): якщо WebGL недоступний, показуй під картками короткий нейтральний напис «3D-перегляд недоступний у цьому браузері» один раз (мовами uk/en/de), не на кожній картці.

## Що має бути в PR

1. Код, нові моделі, постери, тести, оновлений `README.md` та `assets/vendor/README.md` (версії, SHA-256, ліцензії для кожного нового локального файла).
2. Опис PR українською: що зроблено, порівняння «до/після» зі скриншотами, вага кожної моделі до і після, що перевірено в браузері й що ні (телефони, Firefox, Safari, повільні мережі).
3. Перелік змін, які треба врахувати при деплої (`./deploy-worker.sh` бере `assets/` і `data/` автоматично; нові файли мають лежати в цих теках).
4. План на 2–3 наступні кроки.

Не вигадуй фактів про сайт: усе потрібне є в репозиторії. Не став мені питань: роби обґрунтований вибір сам і поясни його в описі PR.
