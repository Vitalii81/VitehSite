# Адмінка ViTeh на Radxa: інструкція власника

Ви редагуєте сайт **приватно на Radxa**, там же дивитесь результат на окремому порту й лише потім публікуєте на Cloudflare **з основного ПК**
наявним скриптом деплою. Адмінка не виставлена в інтернет, а секрети Cloudflare ніколи не потрапляють на Radxa.

```
браузер (LAN / Tailscale) ─► Radxa uhttpd :8082 ─► CGI python3 ─► чернетка ─► «Зібрати пакет» ─► builds/<id>/site
                          └► Radxa uhttpd :8083 (перегляд зібраного, тека staging/…/preview)
основний ПК:  ./deploy-from-radxa.sh <id> ─► ssh+tar ─► перевірка sha256 ─► deploy-worker.sh --source ─► Cloudflare
                                                        └► після успіху Radxa позначає версію «опублікована»
```

## 1. Що потрібно на Radxa

| Вимога | Як перевірити |
| --- | --- |
| `python3` 3.7+ зі стандартною бібліотекою (`fcntl`, `hashlib`, `tarfile`) | `python3 -V` |
| `uhttpd` і procd (OpenWrt/iStoreOS) | `ls /usr/sbin/uhttpd /etc/rc.common` |
| ≥ 200 МБ вільного місця (одна збірка ≈ 3,5 МБ, 20 збірок ≈ 70 МБ, плюс ваші фото й моделі) | `df -h /srv` |
| приватна адреса для прослуховування: `127.0.0.1` і Tailscale-адреса | `tailscale ip -4` |

Ні Node, ні Docker, ні постійних демонів не потрібно.

## 2. Встановлення

**На основному ПК** (копіює код і файли сайту на Radxa через ssh, ключ `~/.ssh/viteh_ai_radxa_ed25519`, якщо він є):

```sh
./radxa-admin/push-to-radxa.sh user@radxa
```

**На Radxa** (спершу «суха» перевірка, нічого не змінює):

```sh
sh /srv/fwportal/admin-incoming/radxa-admin/install-on-radxa.sh --dry-run
sh /srv/fwportal/admin-incoming/radxa-admin/install-on-radxa.sh
sh /srv/fwportal/admin-incoming/radxa-admin/install-on-radxa.sh --set-password
```

Що робить інсталятор (і чого він **не** робить). Адмінка працює як **власна невелика служба `uhttpd`** (procd, `/etc/init.d/vadmin`), бо CGI на цій Radxa працює через uhttpd, а не через nginx. **nginx і його конфіг не змінюються взагалі.**

1. Перевіряє python, `uhttpd`, procd, місце, порти й що кожна адреса приватна (`127.0.0.1`, LAN, Tailscale `100.64.0.0/10`; публічні адреси відхиляються).
2. Записує відповіді основного порталу (`http://127.0.0.1/`, додайте свої адреси через `--probe URL`) **до** змін.
3. Ставить код у `/srv/fwportal/admin/` (веб-файли й CGI-обгортка в `docroot/`), дані в `/srv/fwportal/staging/viteh-site/`.
4. Пише `/etc/init.d/vadmin` із двома екземплярами uhttpd: адмінка з CGI на `:8082` і перегляд без CGI на `:8083`, лише на ваших приватних адресах (типово `127.0.0.1` і Tailscale-адреса). Порти 8081 (вже зайнятий) і 8080/80 не використовуються.
5. Вмикає й запускає службу, порівнює відповіді основного порталу з кроком 2, перевіряє сторінку адмінки, CGI (відповідь 401/503 без входу) і порт перегляду.
6. **Будь-яка помилка** на кроках 3–5: служба зупиняється й видаляється, портал перевіряється ще раз.

Він не чіпає `/srv/fwportal/reserve/`, `radxa-reserve/`, `/api/mail`, `/api/files`, `/api/bridge`, системний `/cgi-bin/*` і не додає тунель `viteh-lab`.
Параметри: `--listen IP` (можна кілька), `--admin-port`, `--preview-port`, `--probe URL`. Оновити лише код і файли сайту (службу не чіпає):
`push-to-radxa.sh`, потім `install-on-radxa.sh --update-code`. Видалити: `install-on-radxa.sh --uninstall` (служба зникає; чернетка й збірки лишаються; `--purge-data` видалить і їх).
Обмеження uhttpd: він не додає заголовки безпеки (CSP, X-Frame-Options), які давав би nginx. Для приватної адмінки в tailnet це прийнятно; запуск з `-D -S` вимикає списки тек і символічні посилання назовні.

### Спробувати без Radxa
```sh
python3 radxa-admin/dev-server.py        # адмінка http://127.0.0.1:8082/, перегляд http://127.0.0.1:8081/ (лише для dev-сервера)
```
Дані лежать у `radxa-admin/.dev-data/` (не потрапляє в git). Фразу входу виводить сервер.

## 3. Вхід і безпека

- Адреса: `http://<tailscale-адреса Radxa>:8082/` (з дому: `http://<LAN-адреса>:8082/`). Це **http**: трафік у Tailscale шифрується самим Tailscale; у LAN він відкритий, тож для LAN розгляньте лише Tailscale.
- Фраза входу: від 20 символів, у файлі `/srv/fwportal/admin-secret/auth.json` лише PBKDF2-хеш (права 0600), у репозиторії й логах її немає. Змінити: `--set-password`; скасувати всі сесії: `python3 /srv/fwportal/admin/vadmin-cli.py revoke-sessions`.
- 5 невдалих спроб з однієї адреси блокують її на 15 хв (і є загальний ліміт). Сесія 8 год, cookie `HttpOnly` + `SameSite=Strict`; усі зміни вимагають службового заголовка й `Origin` свого хоста.
- Файли: лише JPEG/PNG/WebP/AVIF до 5 МБ і `.glb` до 8 МБ (перевірка першими байтами, випадкові імена, SVG відхиляється, `.glb` має бути самодостатнім). Усе, що ви вводите, екранується; у довгих текстах дозволено абзаци, `**жирний**`, `[текст](https://…)` і списки з `- `.

## 4. Щоденна робота

Вгорі завжди видно стан: **Чернетка** (зберігається сама через ~1 с), **Зібрано** (остання збірка; позначка «є зміни після збірки»), **Опубліковано**.

| Розділ | Що там |
| --- | --- |
| **Розділи** | Вмикання й вимкнення розділів головної (hero, довіра, послуги, AI-агенти, процес, проєкти, стек, ціни, FAQ, контакти). Вимкнений розділ **не потрапляє в HTML**, його пункт меню теж зникає. Для hero можна підставити своє фото. |
| **Послуги** | Вмикання заводських послуг, додавання своїх «з шаблону» і редагування. Для кожної послуги можна замінити або додати 3D-модель (`.glb`, до 8 МБ); заводський постер при заміні прибирається, картка показує звичайну картинку, поки не буде нового постера. |
| **Картки проєктів** | Вмикання, заміна фото та `.glb`-моделі без правки коду; нові картки з шаблону. Модель потрібна 3D-галереї. |
| **Додаткові розділи** | Блоки з бібліотеки або з шаблонів («Про нас», «Заклик до дії», «Галерея»), що з'являються на головній перед контактами. |
| **Віджети й ефекти** | 3D-галерея (вимкнена: у пакеті немає ні скрипта, ні бібліотеки, ні моделей) і ефекти (погойдування, поява при прокрутці). |
| **Тексти** | Усі тексти сайту трьома мовами. Позначка ⚠: заповнено не всі мови (порожня мова покаже наявний текст). «До заводського» скасовує зміну. |
| **Сторінки** | Нова сторінка з шаблону («Послуга», «Лендінг продукту», «Про нас», «Контакти», «Порожня») отримує адресу `/s/<адреса>/`. Адреса: `a-z`, `0-9`, `-`; службові (`api`, `admin`, `assets`, `s`, `data` …) заборонені. Прапорець «У меню» додає її в навігацію. |
| **Редактор сторінки** | Список блоків: ↑/↓ (працює на телефоні), перетягування (додатково), дублювати, вимкнути, видалити; праворуч поля блока. 14 блоків: hero, послуги, картки проєктів, AI-агенти, кроки, стек, ціни, FAQ, форма, текст із зображенням, галерея фото, 3D-галерея, заклик до дії, роздільник. «Якір» дозволяє вести посилання `#якір` на блок. |
| **Форми** | Поля, типи (рядок, email, телефон, довгий текст, список, прапорець), обов'язковість, підписи, згода, текст успіху. Нові форми з шаблонів: «Запит на проєкт», «Ремонт електроніки», «Консультація». Форма вставляється блоком «Форма». |
| **Файли** | Бібліотека завантажень. Невикористані файли старші за добу прибираються під час наступної збірки; використані в чернетці чи збірках видалити не можна. |
| **Версії й публікація** | Список із 20 останніх збірок: перегляд, відкат чернетки, команда публікації. |

Стандартна форма контактів на головній **не змінюється**: її тексти редагуються в «Текстах» (`contact.form.*`), а набір полів лишається заводським.

## 5. Зібрати → переглянути → опублікувати

1. **Зібрати пакет.** Спершу автоматична перевірка; пакет **не збирається**, поки є помилки (показуються списком): сторінка без блоків, порожнє обов'язкове поле (хоча б одна мова), відсутнє зображення, посилання на вимкнену сторінку чи розділ, форма без email-поля, дубль адреси, два блоки карток на сторінці. Потім збірка: вимкнене прибирається, сторінки рендеряться статично, формується `sitemap.xml` (лише з увімкнених сторінок) і `forms.json`, а на завершення сканування на запити до сторонніх хостів (за наявності збірка зупиняється).
2. **Перегляд.** `http://<адреса Radxa>:8083/` показує останню збірку. Форми на перегляді нічого не надсилають: Worker приймає запити лише від справжніх доменів сайту.
3. **Опублікувати.** Адмінка сама не публікує, а показує команду. На основному ПК (поруч із `deploy-worker.sh`):

```sh
export RADXA_SSH=user@radxa
./deploy-from-radxa.sh                    # остання збірка
./deploy-from-radxa.sh 20261104-011914-5ef91eab   # конкретна
```
Скрипт тягне пакет по ssh+tar, **перевіряє SHA-256 кожного файла за маніфестом** (і відсутність зайвих), запускає `deploy-worker.sh --source <тека>` і лише після успіху позначає версію «опублікована» на Radxa. З ключем `~/.ssh/viteh_ai_radxa_ed25519`, як `mirror_to_radxa`.

Щоб у `deploy-worker.sh` працював режим `--from-radxa [<id>]`, додайте в розбір аргументів (на самому початку):
```sh
--from-radxa) shift; exec "$(dirname "$0")/deploy-from-radxa.sh" "$@" ;;
```
Після деплою резервний знімок у `reserve` робить сам `deploy-worker.sh`, як і раніше.

**Вимоги до Cloudflare-налаштувань (перевірте один раз):**
- Форми з адмінки йдуть на `/api/form`. Worker читає опис форми з **опублікованого** `/forms.json`. Для цього в `wrangler.toml` має бути прив'язка `binding = "ASSETS"` в `[assets]`; без неї Worker звернеться до `/forms.json` по HTTP свого ж домену (теж працює, якщо `run_worker_first` не охоплює цей шлях).
- `/s/<адреса>/` віддається як `s/<адреса>/index.html` (стандартна поведінка статичних ресурсів Cloudflare).

## 6. Відкат

**Версії й публікація → «Відкотити чернетку»** повертає редактор до стану вибраної збірки (поточна чернетка замінюється). Після цього «Зібрати пакет» створить нову версію. Щоб швидко повернути на сайті стару версію, опублікуйте її id: `./deploy-from-radxa.sh <старий-id>`. Зберігаються 20 останніх збірок і завжди та, що опублікована.

## 7. Скільки це «важить» (виміряно на ПК, Python 3.11; на Radxa буде повільніше, пам'ять приблизно та сама)

| Операція | Пік пам'яті |
| --- | --- |
| Відкриття адмінки / збереження чернетки (CGI) | ≈ 17 МБ |
| «Зібрати пакет» (31 файл, 1,8 МБ) | ≈ 17 МБ, < 0,1 с |
| Завантаження `.glb` на 8 МБ (межа) | ≈ 25 МБ |
| Диск | ≈ 3,5 МБ на збірку (до 20) + ваші файли (ліміт 300 МБ / 200 файлів) |

Один процес на запит, нічого не працює у фоні. Хешування фрази (200 000 ітерацій PBKDF2) займає частки секунди на ПК; на Radxa очікуйте 0,3–1 с при вході.

## 8. Чого не вдалося перевірити без реальної Radxa

Я не бачу Radxa й не мав доступу до `radxa-reserve/`, `ai-family.py` та `deploy-worker.sh` (вони в іншому репозиторії), тому:

- **Інсталятор** перевірено на підробних `uhttpd`, службі й `curl` (11 сценаріїв), а також прочитано реальні умови на Radxa: `/etc/rc.common` і `/usr/sbin/uhttpd` є, Python 3.10, потрібні модулі є, порти 8082/8083 вільні, Tailscale-адреса `100.68.170.111`. Запуск службою процд на справжній Radxa ще не робився: BusyBox `awk`/`sed`/`wget`/`df` і поведінка `uhttpd` при CGI-обгортці перевіряються першим `--dry-run` та першим встановленням.
- **CGI-обгортка:** `uhttpd` передає CGI заголовки запиту (`HTTP_ORIGIN` тощо), тіло через stdin і `Status:` у відповіді; це стандартна поведінка, але на справжній Radxa перевіряється кроком «admin API answers 401/503».
- **Перегляд** обслуговує фіксована тека `staging/…/preview`, яку кожна збірка (і відкат) перезаписує: uhttpd обчислює корінь один раз при старті, тож посилання `builds/current` для нього не годилось.
- **`deploy-from-radxa.sh`** перевірено з підробним `ssh` і підробним `deploy-worker.sh`. Режим `--source <тека>` справжнього скрипта я не бачив: передбачено, що тека має вигляд кореня сайту (`index.html`, `assets/`, `data/`, `s/`, `sitemap.xml`, `forms.json`).
- **`/api/form` на справжньому Worker/Cloudflare** не запускався: перевірено тестами з підміною `cloudflare:email`. Реальна відправка листа й запис у чергу на Radxa потребують вашої перевірки.
- Браузерна перевірка адмінки зроблена лише в Chromium (десктоп і 390 px), через `dev-server.py`, а не через nginx.
- Python на Radxa: код перевірено на синтаксис 3.7, а запускався лише на 3.11.

## 10. Типові проблеми

| Симптом | Що робити |
| --- | --- |
| «Пароль не налаштовано» | `install-on-radxa.sh --set-password` |
| «Забагато спроб» | зачекайте 15 хв або видаліть `/srv/fwportal/admin-secret/attempts.json` |
| 502/«Внутрішня помилка» | `logread | grep -i uhttpd`; перевірте, що служба працює (`/etc/init.d/vadmin status`) і що `docroot/cgi-bin/vadmin-api` має право виконання |
| «Чернетку змінено в іншій вкладці» | оновіть сторінку (F5): інша вкладка зберегла новішу версію |
| Перегляд `:8083` дає 404 | ще не було збірки |
| Збірка зупинилась на «запити до сторонніх хостів» | у вихідних файлах сайту є посилання на CDN чи шрифти: приберіть їх (сайт має працювати без зовнішніх запитів) |
| Після оновлення файлів сайту (`git pull` на ПК) нічого не змінилось | знову `push-to-radxa.sh` і `install-on-radxa.sh --update-code`, потім «Зібрати пакет» |

## 11. Структура

```
radxa-admin/
  install-on-radxa.sh   інсталятор (служба uhttpd/procd, перевірки, автовідкат, --uninstall, --update-code, --set-password)
  push-to-radxa.sh      копіювання на Radxa (на ПК)
  deploy-from-radxa.sh  публікація пакета з Radxa (на ПК, поруч із deploy-worker.sh)
  vadmin-cli.py         list | export | verify | mark-published | build | set-password | revoke-sessions
  dev-server.py         локальна спроба без nginx
  cgi/vadmin.py         CGI-вхід (URL /cgi-bin/vadmin-api, через обгортку з docroot)
  lib/vadmin/           core, schema, check, build, render, richtext, uploads, auth, api
  web/                  index.html, admin.js, admin.css
  tests/                test_vadmin.py (Python unittest)
data/blocks.json        бібліотека блоків і схеми полів       data/templates.json   шаблони (послуга, картка, розділ, сторінки, форми)
worker/forms.mjs        перевірка заявок з форм адмінки      assets/blocks.css, assets/forms.js   стилі й скрипт згенерованих сторінок
```
